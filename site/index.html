orchy · runs agent flows

A prompt asks.
Orchy enforces.

You declare the steps and the rules. Orchy runs the steps, enforces the rules, and records what each step did. A coding agent is good at one step and poor at a long one — so Orchy holds the control flow, and gives each step one job, one tool list, and one contract.

five invariants

What Orchy guarantees

Every rule is enforced by the runner, not requested by the prompt. validate() refuses a rule it cannot check, so a rule never looks enforced when it is not.

01

Tools

A step calls only the tools it declares. A harness refuses a tool it cannot supply — it never drops one in silence.

02

Contract

The value of a step must match its JSON Schema. A step that answers something else fails. The rule works both ways: what reaches a step must match what it takes.

03

Order

A step starts only after every step it needs passes. Everything whose needs have passed runs in the same wave, in parallel.

04

Limit

A cycle stops at its declared limit, and a flow declares a budget in dollars. A flow cannot run forever, and every attempt counts — including the ones a cycle threw away.

05

Provenance

Orchy records what each step changed in the workspace. A step that promises changes: nothing — or changes: { paths: [docs] } — fails when anything else moved. This catches what bash does behind rule one: the record says what happened to each path — added, changed, deleted, renamed, restored, or moved.

how it works

A flow is data, not code

So the TypeScript API, a YAML file, and the graphical editor all produce the same flow — and one flat pipeline runs it.

the pipeline
A run is a state machine on disk. It writes its state after every step, so a gate and a crash recover the same way — and orchy resume continues either one, even in CI.
Each run is a child process. The daemon starts orchy run per run and indexes what it writes. A run that hangs or dies takes nothing with it; four run at once.
The record is a standard. One ATIF v1.7 trajectory per run holds the tool calls, the reasoning, the tokens, and the cost of every step — including the attempts a cycle threw away.
the flow file

One file holds the whole contract

Hover a rule to see where it lives. The same flow writes as YAML, as TypeScript with typed contracts, or as a drawing in the editor — a test keeps them the same.

flow.yamlvalid, whole, and checked
name: research
workspace: { kind: git, path: . }
harness: claude               # only claude supplies the web tool
model: sonnet
budget: 10                    # stop before the next wave at $10
takes:
  type: object
  required: [question]
  properties: { question: { type: string } }

steps:
  - id: question
    kind: agent
    prompt: prompts/question.md  # reads {{ question }}
    tools: []
    returns:
      type: object
      properties: { angles: { type: array } }

  - id: reader
    kind: agent
    needs: [question]
    fanout: { step: question, key: angles }  # one reader per angle
    prompt: prompts/read.md
    tools: [web]
    returns:
      type: object
      properties: { sources: { type: array } }

  - id: brief
    kind: agent
    needs: [reader]
    model: opus                 # the one step that earns the big model
    prompt: prompts/brief.md
    tools: [write]
    returns:
      type: object
      properties: { file: { type: string } }

  - id: check
    kind: agent
    needs: [brief]
    prompt: prompts/check.md
    tools: [read, web]
    changes: nothing            # reads the sources again, moves no file
    returns:
      type: object
      properties: { approved: { type: boolean } }
    cycle: { to: brief, when: { approved: false }, limit: 2 }

  - id: approve
    kind: gate                  # the run persists; a person answers
    needs: [check]
    question: Ship the brief?
    returns:
      type: object
      properties: { ok: { type: boolean } }
A budget in dollars The run stops before the next wave when it has spent it. Every attempt counts, including the ones a cycle threw away. A budget needs a harness that reports a cost, so a flow on a free provider declares none.
What the flow takes --with '{"question":"…"}' is checked against this schema before the first step spends a token. A name nothing supplies fails at the door.
A fanout One step runs once per member of a list an earlier step computed — a panel of reviewers is one block of YAML.
A harness and a model per step Read with a cheap model and keep the big one for the step that earns it. A step names its own harness too, so claude and pi run side by side, local Ollama included.
A promise: changes Bounds what a step may touch. The workspace record catches what bash does behind the tool list.
A cycle Sends the work back until it passes, at most limit times. A retry is just a cycle to the step itself, on the word failed.
A gate Stops the run and waits for a person. The process ends, the run persists, and orchy resume answers it — so a flow works in CI.

Adversarial review, for real

The reviewer runs on a different harness and a different model, reaches no tool that can change a file, and its approved: false is a machine-checked value — not a vibe in a transcript. Escalate to a person at the limit.

Unattended, but bounded

A schedule or a webhook starts the flow, the budget caps the spend, the cycle caps the loops, and a gate holds anything irreversible until a person answers — from the page, or orchy resume in CI.

Cheap where it can be

Fan a prompt out over a list with a local model, keep the expensive model for the one step that earns it, and let a plain command do what needs no model at all.

An agent drives Orchy too

orchy mcp serves the same engine over the Model Context Protocol, as ten tools: a coding agent writes a flow, hears every problem from validate(), runs it, follows it, and answers a gate. A flow that does not validate is refused at the write, with every problem named, so a broken one never runs.

A step reaches that door too, by declaring the orchy tool — and starts bounds what it may start: which flow files, and how many runs. The door counts from the state on disk, so a model cannot talk its way past the bound.

install

Node 22.18+, no build step

Orchy is on npm as @krimvp/orchy, because the bare name belongs to another package. From a clone it needs no build at all: Node strips the types, so the source runs as it is.

terminal 
$ npm install -g @krimvp/orchy
$ orchy run flow.yaml --with '{"issue":412}'
# or from a clone, which runs the TypeScript as it stands
$ git clone https://github.com/krimvp/orchy && cd orchy && npm install
# the daemon and the page
$ npm run ui:build && node src/cli.ts daemon   # http://127.0.0.1:4000
# or hand the engine to an agent
$ claude mcp add orchy -- npx @krimvp/orchy mcp
